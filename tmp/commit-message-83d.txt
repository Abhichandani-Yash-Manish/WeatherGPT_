DeepSeek as the primary provider: sub-second chat, a written answer for point readings

The reader supplied a DeepSeek key after the OpenRouter free-models-per-day quota was exhausted. The key lives
in data/runtime/model-config.json, which is git-ignored; it is never logged and never returned.

- DeepSeekClient speaks the OpenAI-compatible endpoint with deepseek-chat. DeepSeek accepts a JSON object reply,
  not a JSON schema on the wire, so the schema travels in the system message and the reply is parsed exactly as
  the OpenRouter client's is and validated by the same checks. Every call records its model, attempts, latency
  and tokens (including cache hits), so a paid turn can be accounted for.
- WEATHERGPT_PROVIDERS now takes deepseek_first (the reader choice, and the configured default when a DeepSeek
  key exists), deepseek, cloud_free or local. The free OpenRouter ids stay behind the paid endpoint as failover,
  and the deepseek-only policy with no key has no provider at all rather than falling back on its own. A refused
  key disables the client for the process, a missing balance is named, a rate limit is retried once.
- the written answer for a point reading now uses tool-owned place_label and window_label strings ("Surat",
  "17 Sep 2026 09:30-12:30 IST") instead of the gazetteer label and raw ISO timestamps, and carries the
  deterministic source clause into the answer. Measured: "In Surat, for the window 17 Sep 2026 09:30-12:30 IST,
  the forecast rainfall is 0.4 mm. This is a model forecast at the selected place point, not an observation or
  district average. Source: GFS forecast; conditions can change."
- the written answer applies to a point reading only: a short sentence list of at most four lines and 600
  characters. The marine turn with 72 hourly facts kept the typed renderer, measured, so a laid-out record is
  never rewritten by the model.
